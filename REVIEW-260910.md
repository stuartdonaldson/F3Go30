(`PaxCache` / `CacheService` / roster index), lock discipline on read-modify-write properties,

## P1 — Fix before the next release

### 1. `contextDate` override is silently defeated on the dashboard

**Where:** `static-pages/src/index.html:4931` (`loadDashboard_`), against
`script/dashboardWebapp.js:2579-2581` and `script/go30tools.js` `resolveContextDate_`.

**What happens.** `callApi` faithfully sends `contextDate` on every request
(`static-pages/src/index.html:1561`), and the server honours it — `handleCheckinDashboard_`
computes `realToday` from `resolveContextDate_`. But the *viewed date* comes from a separate
client field:

```js
dateISO = dateISO || isoDate_(new Date());          // index.html:4931 — browser clock
```

The server then does `viewDate = parseIsoDateLocal_(payload.dateISO)` and resolves the month
from `viewDate`, not from `realToday`. So with `?contextDate=2026-06-15` on a machine whose real
date is 2026-09-10:

| value | resolves to |
|-------|-------------|
| server `realToday` | 2026-06-15 ✅ |
| client `dateISO` | 2026-09-10 ❌ |
| `resolveDashboardMonth_(viewDate)` | **September's tracker**, not June's |
| `reportedCutoff = viewDate > realToday ? viewDate : realToday` | 2026-09-10 — the override loses |
| `useHandle` month compare (`:2592`) | compares against the wrong month key |

**Impact.** The documented mechanism for deterministically testing month-boundary fallback
(CLAUDE.md §`setContextDate`, `F3Go30-31w5.1`) does not work for the dashboard — the single
screen where month-boundary behaviour is hardest to get right. Any live-check that sets a context
date and then asserts dashboard behaviour is asserting against the real month and passing for the
wrong reason. Note the bonus path already got this right (`:5140` uses `bonusContextDate_()`),
which is what makes the dashboard gap easy to miss.

**Resolution.** Introduce one client-side context-aware clock and route every "today" through it:

```js
// One place the client decides what day it is. CONTEXT_DATE_ is the dev/SIT override
// (index.html:1181); absent it, the device clock. Mirrors the server's resolveContextDate_.
function contextToday_() {
  return CONTEXT_DATE_ ? parseIsoDate_(CONTEXT_DATE_) : new Date();
}
function contextTodayIso_() { return isoDate_(contextToday_()); }
```

Then replace the default at `:4931` with `contextTodayIso_()`. This is finding #2's fix as well —
do them together.

**Verification.** Extend `tests/playwright/*-live-check.spec.js` with a spec that sets a Config
context date in a prior month via `setConfigValue`, loads the dashboard with the matching
`?contextDate=`, and asserts `monthKey` in the response equals that prior month. Restore the
original value afterwards (see the SAFETY note in `announcement-splash-live-check.spec.js`).

### 2. Seven copies of "what day is it" on the client

**Where:** `static-pages/src/index.html` lines 2411, 3378, 4214, 4460, 4931, 4989, 5222.

Each is a bare `isoDate_(new Date())`. None consults `CONTEXT_DATE_`. The server, by contrast,
has exactly one resolver (`resolveContextDate_`) with a documented precedence chain
(request field → Config row → clock) and a PROD guard.

This is precisely the failure mode the project's own standard names: *"Duplicated logic drifts: a
fix, guard, or field lands on one copy and gets forgotten in the others"* (CLAUDE.md §Code
Quality). Finding #1 is that drift already having happened — the bonus path grew a context-aware
helper (`bonusContextDate_`, `:5140`) and the other six sites did not.

**Resolution.** Land `contextToday_()` / `contextTodayIso_()` as above and convert all seven call
sites. Add a guard to `test/test_static_page_client_invariants.js` asserting that
`isoDate_(new Date())` appears **zero** times in the built page outside the helper's own body —
that file already does this style of source-level invariant check, so the pattern is in place.

### 3. Bonus pill series is O(roster × days × entries) per dashboard load

**Where:** `script/BonusTypes.js` `computeBonusSeriesForPax_` / `computeBonusPillsAsOf_`, called
from the roster loop at `script/dashboardWebapp.js:2699`.

```js
function computeBonusSeriesForPax_(entries, f3NameNorm, dayDates, monthStart) {
  return (dayDates || []).map(function(d) {
    return computeBonusPillsAsOf_(entries, f3NameNorm, d, monthStart);   // scans ALL entries
  });
}
```

`computeBonusPillsAsOf_` walks the **entire** month's bonus-entry array and discards every row
whose `nameNorm` doesn't match — then it is called once per day, per PAX. For a 30-PAX roster on
day 31 with 300 bonus entries in the month, that is **30 × 31 × 300 ≈ 279,000 iterations**, each
doing a date comparison, a `bonusTypeDef_` lookup and a key concatenation. Roughly 97% of that
work is the name filter throwing rows away.

This sits inside `rosterLoopMs`, which the telemetry at `:2758` already measures — the number is
there to confirm against.

**Impact.** Directly on the end user's dashboard load, and it grows with the square of program
success: more PAX *and* more bonus entries. It is the load-time cost most likely to degrade
without anyone changing code.

**Resolution.** Bucket once, then sweep forward. Group entries by `nameNorm` a single time before
the roster loop (O(entries)), sort each bucket by date, then accumulate across days instead of
recomputing from scratch per day:

```js
/** entries -> {nameNorm: [entry, ...]} sorted by date. Built once per dashboard load. */
function groupBonusEntriesByPax_(entries) { /* ... */ }

/** Forward sweep: O(thisPaxEntries + days) instead of O(days × allEntries). */
function computeBonusSeriesForPax_(paxEntries, dayDates, monthStart) { /* ... */ }
```

New cost: O(entries) once, plus O(paxEntries + days) per PAX ≈ **300 + 30×(10+31) ≈ 1,500
iterations** — a ~180× reduction on the numbers above. `computeBonusPillsAsOf_` should stay as-is
for its single-point callers; the series function is the one to rewrite. It is pure and already
unit-tested (`test/test_bonus_types.js`), so this is a low-risk refactor with a direct before/after
measurement available in `rosterLoopMs`.

## P2 — Address in the next maintenance pass

### 5. Two full-store `getProperties()` fetches per dashboard load

**Where:** `script/PaxCache.js:120` (`getPaxCacheRowsBulk_`) and `:833`
(`getPaxHistoryEntriesBulk_`), both called from `handleCheckinDashboard_`.

Each independently calls `PropertiesService.getScriptProperties().getProperties()`, which returns
the **whole** store — tracker rows, responses rows, history windows, goals records, roster
indexes, sessions, dedupe keys, `WEBAPP_URL`, the admin secret. The store is bounded at 500 KB
(documented at `PaxCache.js:41`), so a warm deployment transfers and JSON-parses up to 1 MB per
dashboard load to read two subsets of the same data.

The move from per-key `getProperty()` to bulk was the right call and is well justified in the
docstrings (~13× measured). The remaining win is not doing it twice.

**Resolution.** Memoize the snapshot for the lifetime of one script execution:

```js
var paxCacheStoreSnapshot_ = null;   // one execution == one request in GAS

/** Whole-store snapshot, fetched at most once per execution. Read-only —
 *  every write path still goes through setProperty/setProperties directly, and
 *  invalidates this snapshot so a later read in the same execution sees the write. */
function paxCacheStore_() {
  if (paxCacheStoreSnapshot_ === null) {
    try { paxCacheStoreSnapshot_ = PropertiesService.getScriptProperties().getProperties() || {}; }
    catch (e) { paxCacheStoreSnapshot_ = {}; }
  }
  return paxCacheStoreSnapshot_;
}
function invalidatePaxCacheStoreSnapshot_() { paxCacheStoreSnapshot_ = null; }
```

Point both bulk readers at `paxCacheStore_()`, and call `invalidatePaxCacheStoreSnapshot_()` from
every `setProperty`/`setProperties`/`deleteProperty` wrapper in the file. GAS gives each request
a fresh global scope, so there is no cross-request staleness risk — but state that explicitly in
the docstring, because it is the one assumption that makes this safe.

**Secondary:** nothing currently reports store *size*. Add the byte total of the snapshot to
`paxCacheStatsForLog_dw_()` (already merged into the `checkinWebapp.dashboard` event at `:2758`)
so the 500 KB ceiling becomes visible in Axiom before it is hit, not after. The nightly purge
(`purgeStalePaxCache_`) is well designed but currently runs blind to how close the store is.

### 6. Scorecard team colors are rank-derived, so they change between loads

**Where:** `static-pages/src/index.html:4553` (`scorecardTeamColorMap_`), against
`script/dashboardWebapp.js:354` (`groupByTeam_`).

```js
(paxBoard || []).forEach(function(group, i) {
  map[group.name] = 'var(' + SCORECARD_TEAM_COLOR_VARS_[i % 6] + ')';
});
```

`paxBoard`'s order is `groupByTeam_`'s output, which is **sorted by `avgScore` descending**. So a
team's colour is a function of its current rank. When rankings shift — which is the entire point
of the screen — teams swap colours. The docstring's claim ("a team reads as the same colour in
both views") holds within one render and breaks across renders, months, and date-nav steps.

Worse, `groups.sort(function(a, b) { return b.avgScore - a.avgScore; })` has **no tiebreak**.
Early in a month every team is at 0.0, so ordering falls to `Array.prototype.sort`'s behaviour on
equal keys and both the board order *and* every colour can flicker between two loads with
identical data.

**Impact.** Directly undermines the feature's purpose — a PAX cannot learn "we're the green team."

**Resolution.** Two independent fixes, both small:

1. **Stable colour.** Key the palette off the team name, not the index:
   ```js
   function scorecardTeamColorIndex_(name) {          // deterministic, order-independent
     var h = 0, s = String(name || '');
     for (var i = 0; i < s.length; i++) h = ((h << 5) - h + s.charCodeAt(i)) | 0;
     return Math.abs(h) % SCORECARD_TEAM_COLOR_VARS_.length;
   }
   ```
   Collisions are possible with >6 teams; if that matters, assign from a name-sorted team list
   instead — also order-independent, and collision-free up to 6.

2. **Stable sort.** Give `groupByTeam_` a deterministic tiebreak:
   ```js
   groups.sort(function(a, b) {
     return (b.avgScore - a.avgScore) || a.name.localeCompare(b.name);
   });
   ```
   `scorecardPaxComparator_` (`:4581`) already models exactly this — metric, then streak, then
   name. The team sort should match its own precedent.

Unit-testable without the DOM; `test/test_scorecard_pax_comparator.js` is the pattern to follow.

### 7. Dashboard payload ships unrounded floats — ~70 KB per load on mobile

**Where:** `script/dashboardWebapp.js:2385` (`buildRollingAverage_` via `buildDashboardPaxRow_`).

```js
var avg = windowVals.length ? windowVals.reduce(...) / windowVals.length : 0;
series.push(avg);                                   // 0.42857142857142855 — 19 chars
```

Every board row carries a `rollingAverage` of up to 31 raw IEEE doubles. Serialized, a single
value like `0.42857142857142855` costs 19 bytes where 3 decimals (`0.429`) costs 5 — and the
client renders it into an SVG polyline at `:4023` where nothing past ~2 decimals can be seen at
all. Per-row budget on a full month:

| field | ≈ bytes/PAX |
|-------|-------------|
| `rollingAverage` (31 unrounded doubles) | ~590 |
| `bonusByTypeSeries` (31 × 4-key objects) | ~1,400 |
| `daySegments` + `dayValues` + `priorMonthDayValues` | ~300 |
| **total** | **~2.3 KB** |

× 30 PAX ≈ **70 KB of JSON on every dashboard load**, over mobile data, parsed on a phone.

**Resolution, cheapest first:**

1. **Round in `buildRollingAverage_`** — `Math.round(avg * 1000) / 1000`. One line, no contract
   change (the client already treats these as opaque numbers), cuts ~18 KB off a 30-PAX payload.
   Note this is a response-shape change in the sense of
   `docs/OPERATIONS.md §API compatibility with installed clients`, but a numerically compatible
   one: an older installed client plotting `0.429` instead of `0.42857…` renders identically.
2. **Compact `daySegments`** to a single string (`"110-1…"`) rather than an array of status
   strings, decoded client-side. Needs a client change, so gate it behind the same
   tolerate-both-shapes rule the OPERATIONS doc requires.
3. **Leave `bonusByTypeSeries` alone** unless measurement says otherwise — it is what lets
   date-nav scrubbing (`:4366`, `:4432`) repaint without a round trip, which is a genuine
   end-user win worth its bytes.

`captureDashboardRenderTelemetry_` (`:1733`) already records payload array lengths, so the
before/after is measurable from existing telemetry.

### 8. `dashboardWebapp.js` is 3,052 lines with ≥6 distinct responsibilities

**Where:** `script/dashboardWebapp.js` — 19% of all GAS source in one file, and the file with the
most module-alias boilerplate (55 `globalThis` fallback lines, vs. 12 in the next-largest).

Distinct concerns currently co-resident:

| Responsibility | Approx. lines |
|---|---|
| Pure tracker/streak/grid computation | 253–460 |
| Check-in page render + POST routing | 464–532 |
| Site feedback email | 533–595 |
| Cache layer (layout, values, roster, invalidation) | 596–830 |
| Identity resolution (lean/full/handle) | 830–1610 |
| Bonus handlers | 2178–2360 |
| Dashboard assembly | 2360–2830 |

The seams are already clean — the file is *sectioned*, just not *split*. That is what makes this
worth doing rather than dangerous.

**Impact.** Every edit re-reads 3,000 lines of context; the 55-line alias preamble must be
extended for each new cross-file dependency; and the file is the single most likely place for two
concurrent work streams to conflict.

**Resolution.** Extract along the existing section boundaries, lowest-risk first:

1. `dashboardCache.js` — lines 596–830. Self-contained, no identity dependencies, and would give
   the CacheService key strings a single home (they are currently duplicated by string literal
   into `addResponseOnSubmit.js:21` and `PaxCache.js:355`, both with comments apologising for it).
2. `dashboardIdentity.js` — lines 830–1610, the largest and most self-contained block.
3. `siteFeedback.js` — lines 533–595, unrelated to everything around it.

That is ~1,300 lines out, leaving a ~1,700-line handler file. Do these as separate commits with
the existing unit tests as the regression net; `test/test_dashboard_webapp.js` imports by named
export, so the moves are mechanical.

**Related — the alias preamble itself.** The
`(module.exports ? require(...) : null) || globalThis.x` pattern appears ~120 times across
`script/`. It is the correct GAS/Node dual-target idiom, but it is hand-written per symbol. A
single helper would collapse each to one line:

```js
/** Resolves a symbol from a sibling module under Node, or the GAS global scope in production. */
function gasRequire_(modulePath, names) { /* returns {name: fn} */ }
```

Worth doing *while* splitting the file, not as a separate sweep.

### 9. `handleAdminPost_` is a 435-line if-chain across 27 actions

**Where:** `script/WebApp.js:302–737`.

27 sequential `if (payload.action === '...')` blocks. Every unmatched request walks all 27
comparisons; adding an action means editing the middle of a 435-line function; and there is no
programmatic way to enumerate what actions exist — which matters, because
`test/contract/entryPointRegistry.js` is the declared authority on entry points (`H12`) and must
currently be kept in sync **by hand**.

**Resolution.** Convert to a dispatch table:

```js
var ADMIN_ACTIONS_ = {
  setScriptProperties: { readOnly: false, handler: adminSetScriptProperties_ },
  getSheet:            { readOnly: true,  handler: adminGetSheet_ },
  // ...
};
```

Three things fall out for free: constant-time dispatch, one small function per action (each
independently unit-testable), and `Object.keys(ADMIN_ACTIONS_)` becomes a real coverage oracle
that `test/test_entry_point_registry_view.js` can assert against instead of trusting a
hand-maintained list. The `readOnly` flag the registry already tracks becomes data next to the
handler rather than prose in a separate file.

Do this after finding #8 — same file family, and the pattern should be settled once.

### 10. No test file uses `node:test` — 63 files report as 63 assertions

**Where:** all 63 files in `test/test_*.js`; confirmed — zero require `node:test`.

Every file is a sequence of bare IIFEs calling `node:assert/strict`:

```js
(function testHandleSiteFeedbackSendsAgainWhenReportTextEditedProducesNewKey() {
  ...
  assert.equal(sent.length, 2, 'AC4: ...');
})();
```

The names are good and the AC references are excellent. But because nothing registers them with
the test runner, `node --test` sees **one test per file**. Three consequences:

- **Fail-fast per file.** The first failing assertion throws and every later assertion in that
  file never runs. A change breaking five things reports one.
- **The H6/H7/H8 metrics are coarse by roughly an order of magnitude.** `executions: 63` in the
  outcome summary counts files, not cases. "Execution failure rate" and "wall time on failed
  executions" are computed against a denominator ~10× smaller than the real assertion count,
  which flatters both numbers.
- **No per-case name in the JUnit XML**, so `test-results/node-junit.xml` can't tell CI or a
  reviewer *which* AC regressed.

**Resolution.** Mechanical: wrap each IIFE in `test()`.

```js
const { test } = require('node:test');
const assert = require('node:assert/strict');

test('handleSiteFeedback_ sends again when edited report text produces a new key', () => { ... });
```

The function names already read as test names — most conversions are a two-line diff and the body
is untouched. Convert opportunistically as files are edited rather than in one 63-file sweep, but
do the top-level runner change first so new files inherit the pattern. `tools/test-outcome-report.js`
reads the JUnit XML and needs no change — the counts simply become truthful.

### 14. A single global script lock serializes all concurrent check-ins

`LockService.getScriptLock()` is script-global — there is one lock for the entire deployment.
It is taken by `advancePaxHistoryDay_` (`PaxCache.js:911`) and `refreshPaxCacheRowFromSheet_` on
**every check-in write**, plus roster patches, bonus writes, and session writes, each with a 10s
`waitLock`.

F3 check-ins cluster hard — a whole AO reports within minutes of the same workout. Under that
burst every write queues behind every other write, deployment-wide, and a PAX at the back of a
20-deep queue can hit the 10s timeout. The failure is handled gracefully (`lockFailed` is logged
and the write is skipped best-effort, `PaxCache.js:911-915`), but "handled" here means the
history entry silently doesn't advance — the streak the user just earned doesn't appear.

The lock scoping is correct in intent — the comment at `PaxCache.js:219` reasons carefully about
*why* the lock is needed — the constraint is that GAS offers no finer-grained lock.

**Resolution.** Don't restructure; **measure first**. Add the `lockFailed` count and lock wait
duration to the `checkinWebapp.checkin` telemetry event (`dashboardWebapp.js:2157`) so Axiom can
show whether contention is real at current scale. If it is, the mitigation is to make the
history write idempotent-retryable and move it off the request path — but that is a design change
warranting an ADR, not a code tweak, and should not be undertaken on speculation.

### 15. `bootstrapAdminSecret_` is an unauthenticated race on an anonymous deployment

**Where:** `script/WebApp.js:283`, reached at `:310` **before** the secret check.

The webapp is deployed `ANYONE_ANONYMOUS` (stated in CLAUDE.md, and required for the PROD
check-in flow). `bootstrapSecret` is therefore reachable by any caller on the internet, and its
only guard is "a secret isn't already set." Whoever calls first owns admin — including
`setScriptProperties`, `cleanupTracker`, and `teardownEnvironment`.

In steady state PROD this is closed: the property is set and stays set. The exposure is any window
where it isn't — a fresh script project, a restored/recreated deployment, or a property store
cleared by an operator. The design is deliberate and documented (`§3.2`: bootstrap must work
before any secret exists), so this is a **residual risk to record, not a defect to fix blind**.

**Resolution.** Two cheap hardenings that preserve the bootstrap flow:

1. Alert on the transition. `bootstrapAdminSecret_` already logs `bootstrapAdminSecret_.bootstrapped`
   (`:290`) — add an Axiom monitor on that event so an unexpected bootstrap on PROD is noticed
   in minutes rather than never.
2. Log the rejected case too. `already_bootstrapped` currently returns silently; logging it
   surfaces anyone probing for the window.

Also worth noting (very low severity, but free): `payload.adminSecret !== storedSecret` at `:314`
is a non-constant-time comparison. Over a network path with GAS's latency variance this is not
practically exploitable, and no change is recommended — recorded so it isn't rediscovered as new.

## What is working well

Worth stating, because these are the parts a future refactor should be careful not to damage:

- **Cache layering.** Layout / values / roster-index / history are separate caches with separate
  TTLs and separate invalidation, each with a docstring explaining *why* write-through is or
  isn't needed. `buildTrackerValuesFromPaxCache_`'s reasoning about why a whole-sheet blob is
  wrong for single-row writes (`:772`) is exactly the right analysis.
- **Lock discipline.** Every read-modify-write on a shared property is lock-guarded, and the
  reason each lock exists is written down. The `go30hist`/`go30goals` split — separate keys
  specifically to keep lock scopes disjoint (`PaxCache.js:926`) — is a genuinely good call.
- **Boundary-fault classification.** Concentrating infrastructure-vs-code failure classification
  in `tests/harness/outcomes.js`, with a standing rule against per-test `try`/`catch` labelling,
  is the right architecture for a suite that depends on Google.
- **Installed-client compatibility.** Treating the PWA as an independently-versioned client, with
  `clientVersion` on every request and an explicit additive-only contract rule, is discipline most
  projects this size skip.
- **Comment quality.** Comments explain *why*, cite the bead that caused the change, and describe
  what was tried and rejected. This is why the review could be this specific.

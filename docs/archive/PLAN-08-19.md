## How stages were grouped

- **File/context locality**: issues touching the same source files or subsystem are batched
  together so one session's exploration (reading `static-pages/src/index.html`'s transport block,
  finding the name-click mount point, etc.) pays off more than once instead of being re-derived
  cold in a later session.
- **bd dependency order preserved**: every `blocks` edge in the current graph is honored — no
  stage schedules an issue before an issue that blocks it. `related`/`relates-to` edges are noted
  as context to carry forward, not hard ordering.
- **Deliverable value first, frozen work last**: stages that ship something usable now (or need no
  gate at all) are sequenced ahead of anything currently deferred or transitively blocked by a
  deferred issue, even where the deferred work was drafted earlier in the original grouping.
  Hardening work with no infrastructure dependency (signup completeness, Slack-link uniqueness) is
  pulled forward for the same reason — it's cheap, low-risk, and ships value immediately.
- **Elapsed-time gates isolated**: F3Go30-833s.4 requires a month of live PROD data and cannot be
  closed inside any coding session — it's called out as a checkpoint, not folded into a stage's
  AC.
- Epics (`F3Go30-1pqo`, `F3Go30-833s`, `F3Go30-kgzo`, `F3Go30-uz9e`, `F3Go30-6faz`) are tracked in
  whichever stage closes their last remaining child; they need no direct work themselves beyond
  closing once children are done.
